# 02. REST Assured

Статус: завершено 13 октября 2026 года.

REST Assured — Java-библиотека для отправки HTTP-запросов и проверки ответов.
Теорию разбираем на существующих тестах Fake Store API.

## Структура given / when / then

```java
given()
        .spec(requestSpec)
        .pathParam("productId", productId)
.when()
        .get("/products/{productId}")
.then()
        .statusCode(200);
```

- `given` — подготовка запроса: спецификация, параметры, заголовки и тело;
- `when` — отправка запроса выбранным HTTP-методом;
- `then` — проверки полученного ответа.

## Общая спецификация

В `BaseApiTest` через `RequestSpecBuilder` создаётся `requestSpec`. В ней уже
содержатся:

- базовый адрес `https://fakestoreapi.com`;
- ожидаемый формат ответа JSON;
- фильтр REST Assured для Allure.

В тесте `.spec(requestSpec)` применяет эти общие настройки, чтобы не повторять
их в каждом запросе.

## Path parameter

```java
.pathParam("productId", 1)
.get("/products/{productId}")
```

REST Assured подставляет значение `1` вместо `{productId}`. Итоговый путь:
`/products/1`.

## Проверка и извлечение ответа

```java
.then()
        .statusCode(200)
        .extract()
        .as(Product.class);
```

Сначала проверяется HTTP-статус. Затем JSON-ответ преобразуется в Java-модель
`Product`, после чего поля модели проверяются JUnit assertions.

## Первая практика

1. Открыть `BaseApiTest`, `ProductApiTest` и модель `Product`.
2. Проследить путь запроса от `given()` до объекта `Product`.
3. Самостоятельно запустить:

   ```bash
   ./gradlew test --tests api.ProductApiTest
   ```

4. Объяснить своими словами:
   - что находится в `given`;
   - когда фактически отправляется запрос;
   - что проверяется в `then`;
   - зачем используется `requestSpec`;
   - как работает `pathParam`;
   - что делает `.extract().as(Product.class)`.

Тест отсутствующего продукта помечен `@Disabled` из-за дефекта `FKS-001`,
поэтому его пропуск в результате запуска ожидаем.

## Практика 2 — список продуктов

Первый запуск `ProductApiTest` завершился с `BUILD SUCCESSFUL`.

Следующая задача: самостоятельно добавить в `ProductApiTest` проверку
`GET /products`:

1. применить существующий `requestSpec`;
2. отправить `GET` на `/products` без path parameter;
3. проверить HTTP-статус `200`;
4. проверить, что размер массива в JSON больше нуля;
5. логировать ответ только при провале проверки;
6. добавить понятные `@DisplayName`, `@Tag("regression")` и имя метода;
7. запустить только новый метод теста.

Практика выполнена 13 октября 2026 года. Метод
`shouldReturnProductList` самостоятельно добавлен и успешно запущен. Тест
проверяет статус `200`, JSON-формат ответа и непустой массив продуктов.

Важно различать два случая:

- `contentType(ContentType.JSON)` в `given()` описывает формат тела запроса;
- `contentType(ContentType.JSON)` после `then()` проверяет формат ответа.

У `GET /products` нет тела запроса, поэтому request `Content-Type` ему не
нужен. Ожидаемый формат ответа уже объявлен через `Accept` в общей
спецификации, а фактический формат ответа отдельно проверяется после `then()`.

Следующий шаг — разобрать существующий POST-тест: тело запроса, сериализацию
Java-модели и проверки созданного продукта.

## Практика 3 — создание продукта

Существующий POST-тест разобран. Метод переименован в
`shouldCreateProduct`, получил понятное отображаемое имя и 13 октября 2026
года успешно запущен отдельно.

В этом тесте:

- `PostProduct` хранит данные запроса;
- `.body(product)` сериализует Java-объект в JSON и подготавливает тело;
- request `Content-Type: application/json` сообщает серверу формат тела;
- `.post("/products")` отправляет запрос;
- статус `201`, возвращённый `title` и положительный `id` проверяют результат.

Различие закреплено: `.body(product)` только подготавливает сериализованное
JSON-тело, а `.post(...)` в блоке `when` фактически отправляет запрос. Также
закреплено, что request `Content-Type` сообщает серверу формат отправленных
данных, а `body("size()", greaterThan(0))` проверяет непустой массив ответа.
