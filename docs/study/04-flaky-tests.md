# 04. Flaky-тесты

Статус: завершено 14 октября 2026 года.

Flaky-тест — тест, который без ожидаемых изменений в коде и при одинаковых
условиях может то пройти, то упасть. Поэтому его результату нельзя доверять.

Разбираем только способы борьбы из списка:

- рефакторинг;
- выбор более хороших селекторов и локаторов;
- совмещение UI- и API-тестов;
- многопоточный запуск автотестов.

## Практика 1 — распознать flaky-тест

Нужно отличить нестабильный тест от обычного дефекта теста или продукта и
объяснить, почему изменчивый селектор может давать непредсказуемый результат.

После этого сравним локаторы в существующих `TextBoxPage` и
`RadioButtonPage` и выберем потенциальное место для рефакторинга.

Практика выполнена 13 октября 2026 года. Пользователь правильно разделил:

- постоянно падающий тест с неправильным селектором — стабильная ошибка
  теста, а не flaky;
- тест, который то проходит, то падает по тайм-ауту, — flaky;
- постоянный ответ `200` вместо ожидаемого `404` — дефект API, а не flaky.

## Практика 2 — устойчивость локаторов

Сравнить существующие локаторы:

```java
$("#userEmail")
$("label[for='yesRadio']")
$(".text-success")
```

Определить наиболее и наименее устойчивый локатор и объяснить выбор.

Разобраны типы CSS-селекторов:

- `#userEmail` — поиск по ID;
- `.text-success` — поиск по CSS-классу;
- `label[for='yesRadio']` — поиск элемента `label` по атрибуту `for` со
  значением `yesRadio`.

Стабильный ID выбран как наиболее устойчивый вариант. Общий класс
`.text-success` признан слабее: он может измениться или совпасть у нескольких
элементов. Локатор `label[for='yesRadio']` точнее общего класса, потому что
связан с конкретной radio-кнопкой.

## Практика 3 — рефакторинг локатора

У результата Radio Button нет уникального ID или `data-*` атрибута. Поэтому
общий локатор `.text-success` ограничен родительским элементом:

```java
$("p.mt-3 .text-success")
```

Поле самостоятельно переименовано из общего `output` в `selectedValue`.
После рефакторинга `RadioButtonTest` успешно запущен 14 октября 2026 года:
`BUILD SUCCESSFUL` за 42 секунды.

Этот локатор точнее исходного, но всё ещё зависит от CSS-классов оформления.
В рабочем проекте предпочтителен специальный стабильный `data-*` атрибут.

Следующий шаг — разобрать совмещение UI и API для подготовки предусловий и
понять, почему такой подход может уменьшить нестабильность UI-теста.

## Совмещение UI и API

API подходит для быстрой подготовки предусловий без браузера, HTML, локаторов
и лишних UI-ожиданий. UI-тест после этого проверяет только нужное видимое
поведение и пользовательское взаимодействие.

Практически объединять можно только API и UI одного приложения и одной среды:
подготовленные через API данные должны быть доступны проверяемому интерфейсу.
Fake Store API и DemoQA — независимые приложения с разными данными, поэтому
искусственно объединять их в один тест нельзя. Это ограничение проекта
зафиксировано вместо бессмысленного сценария.

### Согласованный практический сценарий

14 октября 2026 года согласован сценарий внутри одного приложения DemoQA Book
Store:

1. через `POST /Account/v1/User` создать уникального пользователя;
2. через `POST /Account/v1/GenerateToken` получить токен;
3. через `GET /BookStore/v1/Books` выбрать существующую книгу;
4. через `POST /BookStore/v1/Books` добавить книгу пользователю;
5. через UI `/login` войти созданным пользователем;
6. на UI `/profile` проверить название добавленной книги;
7. через `DELETE /Account/v1/User/{userId}` удалить пользователя и его данные.

API используется только для предусловий и очистки, а UI — для проверки
видимого пользователю результата. Уникальный пользователь и обязательное
удаление обеспечивают независимость сценария.

### Реализация сценария

Созданы типизированные модели запросов и ответов DemoQA Book Store. Для
несовпадающих имён внешнего контракта применён `JsonProperty`: Java использует
понятные `username` и `userId`, а JSON сохраняет требуемые API имена
`userName` и `userID`.

Следующий этап — API-клиент с отдельной спецификацией DemoQA. Существующий
`BaseApiTest` не меняется, потому что он настроен для Fake Store API.

API-клиент `DemoQaBookStoreApi` самостоятельно реализован. Он умеет создавать
пользователя, получать токен и список книг, добавлять книги и удалять
пользователя. Для запросов используется отдельная спецификация с базовым
адресом DemoQA и Allure-фильтром. Модели и клиент успешно скомпилированы через
`./gradlew testClasses` 14 октября 2026 года.

Следующий этап — выбрать устойчивые локаторы и создать Page Objects для входа
и проверки профиля.

Созданы `LoginPage` и `ProfilePage`. Для формы входа используются стабильные
ID `userName`, `password` и `login`. Профиль проверяет имя пользователя по
`userName-value`, а книгу находит в коллекции элементов с ID, начинающимся на
`see-book-`. API-клиент, модели и оба Page Object успешно компилируются.

Итоговый `BookStoreUiApiTest` создаёт уникального пользователя и добавляет ему
книгу через API, затем входит через UI и проверяет книгу в профиле. Очистка
пользователя выполняется через API в `@AfterEach`.

Первый запуск подтвердил основной сценарий, но упал на очистке с ответом `401
User not authorized!`. Причина: вход через UI выпустил новый токен и сделал
старый API-токен недействительным. Очистка была исправлена: непосредственно
перед `DELETE` тест всегда получает свежий токен. После исправления сценарий
самостоятельно запущен повторно и завершился успешно: `BUILD SUCCESSFUL` за
14 секунд.

Сценарий независим от других тестов: создаёт пользователя с уникальным именем,
сам готовит данные через API и удаляет их после проверки. Он не использует
результаты других тестов и не требует определённого порядка запуска.

## Многопоточный запуск

В `junit-platform.properties` параллельность включена и установлен лимит в два
потока. Однако включение механизма само по себе не переводит все тесты в
параллельный режим. Сейчас `@Execution(CONCURRENT)` явно установлен на
`ProductApiTest`; остальные классы по умолчанию остаются в режиме
`SAME_THREAD`.

Пользователь объяснил, что два рабочих потока позволяют выполнять до двух
тестов одновременно, а `CONCURRENT` не заставляет один тест ждать другой.
Активные методы `ProductApiTest` не используют результат друг друга, и класс
успешно проходил с этой настройкой.

Разобраны и применены все способы из списка: рефакторинг, улучшение локатора,
совмещение UI и API и многопоточный запуск. Для UI+API-практики выбран единый
стенд DemoQA Book Store, поэтому подготовленные через API данные действительно
проверяются в UI того же приложения.
